In Chapter 4, the experiments aim to see if our ESG system can turn sustainability reports (PDFs) into organized, verifiable ESG information. We also want to categorize this information by ESG pillar, aspect, sentiment, and the tone of disclosure, compare these tone results with labels similar to what ClimateBERT uses, and find problems that are important for proving the thesis. We're not just testing one isolated model. Instead, we're testing a whole system that includes reading PDFs with OCR, using large language models (LLMs) to pull out structured data, labeling benchmarks, matching data to an ontology, and using diagnostic dashboards.

We're mainly evaluating our system's step-by-step ESG analysis approach. First, OCR and page extraction turn PDFs into markdown files for each page and OCR data in JSON format. Second, T3 LLM extraction creates structured ESG records, which go into results/esg_records.json. Third, the T1 comparison layer checks these extracted texts against classifications similar to ClimateBERT's, or local versions of them. Fourth, the T2 ABSA-style layer uses rule-based logic, traditional machine learning, and a simple hybrid model that understands context. The last layer combines all these results into tables showing how well our ontology is covered, summaries of problems, agreement scores, and dashboard visuals.

Our code already includes several ways to compare results. For example, code/rule_based.py offers a basic method based on specific words that signal aspect, polarity, and tone. code/classical_ml.py uses a traditional TF-IDF and logistic regression approach. And code/hybrid_model.py uses a hybrid model that understands multiple languages and context by combining sentence embeddings, section details, ontology vectors, and a document-level vector. At the same time, the LLM extraction layer tries out different prompts and models, instead of sticking to just one. This is key because the thesis isn't just about how well things are classified, but also about how stable the data structure is, how complete the fields are, and how useful the extracted information is in practice.

We use seven main prompt templates for our stability analysis, which are important for the thesis: data.md, tone_chain_of_thought_english.md, tone_chain_of_thought_indonesian.md, tone_few_shot_english.md, tone_few_shot_indonesian.md, tone_zero_shot_english.md, and tone_zero_shot_indonesian.md. These templates use three main prompting methods: zero-shot, few-shot, and chain-of-thought, for both English and Indonesian. Our system's backend works with models hosted on OpenRouter, local models compatible with LM Studio or OpenAI, and local inference using Ollama. The thesis dashboard currently shows that the key model comparison we're focusing on is between arcee-ai/trinity-large-preview:free and openai/gpt-oss-120b:free. We also do live runs with other models like arcee-ai/trinity-large-thinking:free, minimax/minimax-m2.5:free, and openai/gpt-oss-20b:free.

This design comes straight from Chapter 3. Chapter 3 explained that it's better to use a varied, modular evaluation strategy instead of just one model. This is because ESG reports are often in two languages, their structure isn't always the same, and they can have issues with OCR and data schemas. So, in Chapter 4, we're testing both how good the final results are and how reliable the system works.

Our system is built around a Python and Streamlit workspace for research. The main part of the system is a Streamlit application with multiple pages (found in pages/), which uses shared code (in code/). Raw data is in data/, processed files are in results/, prompt templates are in prompt/, and documents are in documentation/. This setup is key to our experiment design because each step creates stable intermediate files that we can check or use again later.

For data that has gone through OCR, each document in data/thesis_dataset/ has an ocr_result.json file, markdown files for each page, and images that were pulled out. When we extract data, pages/llm_processing.py saves structured run details to results/esg_records.json and information about background jobs to results/background_llm_jobs/. For benchmark tests, pages/ground_truth.py saves JSONL files that can be resumed to results/t1_results.jsonl and results/t2_results.jsonl. For the thesis report, summary tables and figures are saved to results/revision_analysis/ and results/thesis_workflow_dashboard/.

Here are the main settings for extracting features and for the models we use. The rule-based model uses specific words as triggers for aspect, polarity, and tone. The classical model uses TF-IDF vectors for words and characters, along with logistic regression and one-vs-rest classification for aspects that have multiple labels. The hybrid model, when possible, uses distilbert-base-multilingual-cased, which has a simple hierarchical encoder and a combined prediction head. By default, in code/hybrid_model.py, the encoder's weights are fixed to make it run fast on a CPU. Its design includes a small multi-head attention block for how different sections interact. This setup works well for this thesis because the system is meant to run on regular local research computers and interactive dashboards, not just powerful training servers.

The experiment results also depend on the computing power we have. Our current system can make LLM calls to the cloud via OpenRouter, and it can run local models using LM Studio-compatible setups and models downloaded from Hugging Face. Right now, when we compare to ClimateBERT, we mostly use local downloaded models like distilroberta-base-climate-commitment and similar classification checkpoints. The system notes that a full, direct comparison with a remote ClimateBERT benchmark is something we plan to do later. This means we should interpret the results carefully: the current ClimateBERT comparisons show a good proxy validation, but they aren't yet a definitive external benchmark.

One of the best things about our code is that results can be reproduced. The thesis dashboard shows 1,220 result files, 184 LLM jobs that ran in the background, and saved graphs. The system clearly states that you can remake the visualizations by running scripts like code/visualize_tone_climatebert.py. Also, Streamlit pages like 6_1_Chapter_4_Implementation_Results.py and 6_6_Chapter_4_Results_Visualizer.py let you see these saved files live. So, the experiments are reproducible from an engineering standpoint, even if some of the semantic comparisons aren't fully done yet.

Not all results in Chapter 4 use the same base numbers or the same data. So, we need to understand each comparison based on its specific subset of data. For example, OCR completion looks at the documents we've processed. Tone distributions and agreement tables use the extracted records that have passed extra validity checks. Pilot annotation observations come from a smaller set of data used for review. Because of this, we don't treat every number mentioned in this chapter as if it came from a single, consistent benchmark dataset.

Comparisons are most fair when the exact same piece of extracted text is used throughout all steps. This holds true for our main tone-versus-ClimateBERT comparison, where the text and IDs for each record stay the same for later comparisons. However, when comparing prompts and models, we should only see them as controlled comparisons if we use the exact same data and the same rules for what to accept. If these conditions aren't perfectly met, we consider the results as helpful for diagnosis, not as final, direct comparisons.

We use several main ways to measure how well our system works, because no single measure can show its full quality.

For Research Question 1 (RQ1), the main measurement is how complete the OCR processing is. This means counting how many documents were processed successfully and how many pages are covered in the OCR-processed data. Currently, our dashboard shows that all 23 documents we tracked for OCR are done, covering about 5,512 pages. This measure is good because the system's first job is to work: it needs to turn PDFs into useful files before we can do any ESG analysis.

To check the quality of T3 extraction, we look at several things: how often JSON parsing works, the average number of records per run, how complete the fields are, how often tone is missing, and how much the data schema shifts. JSON parse success rate tells us if a model and prompt create outputs that are structured correctly. Average records per run shows how much data we get. Field completion rate tells us how often all the expected fields are filled in. Missing-tone rate shows how often the tone is left out, which is very important because tone is a key part of this thesis. Schema-drift rate catches fields that are wrong or used for the wrong purpose, like tone values showing up where sentiment should be.

For classification and comparison, we use percent agreement and Cohen's kappa. Agreement just shows how much our tone labels and ClimateBERT-style commitment labels match. Cohen's kappa also accounts for matches that might happen by chance. Our summary shows that the comparison between our tone labels and ClimateBERT-style commitment labels, covering 332 records, has an 83.7% agreement and a Cohen's kappa of 0.645. Higher numbers mean a better match. We prefer kappa over simple agreement because the 'commitment' category appears often.

To check how well we represent information and use our ontology, we use 'ontology coverage'. This measure tells us if the aspects we extract can be linked to paths in our ontology. In the current summary for Research Question 4 (RQ4), we track 52 aspects, and all of them are mapped to ontology paths. While this doesn't mean the meanings are perfectly correct, it does show if our ontology works and is broad enough for later understanding.

To look at interpretive risk for companies, we use a 'greenwashing index.' This is a specific ratio of commitment records to outcome records within each document. Higher numbers mean a greater focus on promises compared to what was actually achieved. This measure is helpful because it turns our tone categories into a signal about governance and disclosure risk that we can understand. However, it's still a rule-of-thumb measure and hasn't been confirmed by outside sources yet.

Simple metrics aren't enough because our system isn't just about classifying single labels. We need more ways to measure its reliability, how easy it is to understand, and its overall usefulness.

First, we use prompt stability metrics to see how much the extraction process is affected by how we phrase our prompts. These include how often parsing succeeds at the prompt level, the average number of records, how often tone is missing, how much the schema shifts, and how complete the fields are. Second, model stability metrics check if improvements in quality hold true for different types of models. Third, we count different ways the system fails. This helps us find specific structural or language issues that cause problems, such as text that's in two languages or mixes them, language that is uncertain or guarded, passive sentences, specific Indonesian regulatory terms, documents with many tables, or cases where the tone is clearly missing.

Fourth, we check our denominators carefully to make sure we interpret results correctly. The file results/revision_analysis/chapter4_tone_denominator_audit.csv clarifies the difference between how much of the whole text is covered and what numbers we use for tone tables. For instance, we use 5,444 items for the overall extracted record coverage. But for tone distribution and agreement, we only use 4,853 items because we remove 591 cases where tone was missing, treating them as quality problems. This is important for our method because we don't want to make our agreement scores seem better than they are, or get them wrong, by including results where the tone was invalid or missing.

Fifth, we count how often specific words or phrases (lexical triggers) appear. This helps us understand the results more easily. These counts show how often triggers related to action, commitment, outcome, hedging, passive voice, regulations, and table layouts appear with the predicted tones. These measures don't replace checking the actual meaning, but they do help explain why some prompts or models might predict too much 'commitment' or miss 'outcome' language.

Together, all these measures give us a more complete picture of how well the system works. OCR metrics check if the system is ready to run. Parsing and completion metrics show how easy the extracted data is to use. Agreement metrics show how much different interpretations overlap. Ontology coverage checks if the semantic mapping is ready. Stability metrics tell us how robust the system is. Failure modes show where the weaknesses are concentrated. Greenwashing ratios and lexical triggers offer specific insights related to the task, going beyond just basic accuracy.
